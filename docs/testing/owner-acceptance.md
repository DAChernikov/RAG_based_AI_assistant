# Owner acceptance scenario

This is the single manual acceptance path for a release. Use a local fake website, a disposable local Git repository and a disposable tenant; never production credentials.

1. Start native Ollama or llama.cpp with Qwen, then run `./scripts/dev-up` (PowerShell: `./scripts/dev-up.ps1`). On later starts the equivalent command is `docker compose --env-file .env.local up -d --build`. Confirm the browser opens `http://localhost:8080`; no terminal bootstrap is part of the normal path. On a cold cache the **Система** step must show BGE-M3 as `model_loading`, while `/ready` remains unavailable until the model is really loaded.
2. In Setup Wizard create tenant `acceptance` and the first administrator. Reload during the model step and confirm progress resumes without asking for the administrator password again. In production-like testing, verify setup is absent without the mounted `SETUP_BOOTSTRAP_TOKEN_FILE`, requires its token when enabled, and returns 409 forever after administrator creation.
3. Configure generation and embedding endpoints in the Wizard, optionally reranker, and run connection checks. Configure or skip Telegram. Finish readiness and enter the product. Confirm refresh survives a page reload and logout invalidates the session.
4. In **Модели**, inspect installed Ollama models, test the self-hosted endpoint and edit the user-facing instructions. If an endpoint needs a token, enter it in the model form and confirm the value is absent after reload. In **Доступ**, create a user and scoped API key; copy the full API key once. Confirm it is not shown on reload and a revoked key returns 401.
5. In **Подключения**, register a local Website source and a local Git source using the typed forms, hints and examples. Enter disposable credentials directly in the relevant connection form and confirm they are absent after reload. Create a knowledge base while selecting both sources; refresh and inspect synchronization/index progress in the same section. Exercise cancel and the advanced activate/rollback/pin controls where appropriate. No step requires pasting arbitrary JSON.
6. Start indexing. Confirm run reaches active, sources/provenance are visible and a second identical request does not create duplicate content/embeddings.
7. Log in as the user, select **Без базы знаний** and ask a general question. Confirm mode `model` and no invented citations. Then select the KB and ask a question covering docs and code. Confirm streaming, route targets, citations, history, feedback, cancel/retry and reconnect.
8. Register a disposable PostgreSQL metadata source using only a credential reference and allowlists. Ask a SQL question; verify one read-only SELECT/WITH, schema validation and safe EXPLAIN. Attempt DDL, multiple statements and an unknown table; each must be rejected.
9. Create another tenant/admin. Verify source, index, job, conversation and SSE identifiers from tenant A return 404/403 in tenant B.
10. Update/delete source content, refresh and index. Confirm unchanged embeddings are reused, removed content disappears from the new active index, then rollback to the previous index.
11. Enable a schedule and confirm repeated scheduler passes are idempotent. Pause/resume it. Run retention dry-run then run; active/pinned versions remain.
12. Stop/restart each worker during a job. Confirm reclaim is fenced, attempts are bounded and no duplicate answer/version appears. Inspect **Диагностика**, DLQ recovery and audit without prompts/secrets.
13. In **Telegram**, select the two credential references, enable and test the bot. Ask a question, rotate the token, then revoke the API key and confirm the next bot request is unauthorized. The bot must apply the config version without image rebuild.
14. Open **Guide**, verify both user and admin flows, toggle the light/dark theme and use the account card at the bottom of the sidebar to change a disposable password. Review metrics/dashboard/alerts, JSON redaction, backup restore drill and `docs/operations/production-checklist.md`. Record result, release SHA, hardware and deviations.

Cleanup: revoke test keys/sessions, delete disposable sources/users/tenant according to policy, stop Compose without deleting volumes needed for diagnosis. Troubleshooting starts with sanitized `/ready`, container health, PostgreSQL durable status and worker event/DLQ runbooks.
